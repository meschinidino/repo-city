## Problem Statement

A developer who vibe-codes with agents cannot see what his repo is or what his agents are doing without reading folders, files, and diffs. Build software that manages agent sessions for a repo as CRUD, renders the repo as a city of modules and connections, shows agents visibly working on that map, and reports back in plain English. Code stays available as drill-down, never as the main surface.

## What Makes This Cool

The pile of code and folders becomes a place you can read at plain sight. You point at a district, start an agent there, watch it build, and get an English report. One real drag action on the city (connect two districts) starts real agent work, so the city is a control surface, not a picture.

## Constraints

- Meta global hackathon (Cerebral Valley): 10 days, submit Nov 4, 9:00 PM ET on the CV platform with all teammates, a 3-minute demo video of only what the team built during the event, and a public GitHub repo.
- Judging: Impact 30%, Use of Meta AI tooling 25%, Technical depth 20%, Demo 25%.
- Anti-project list bans "dashboards as the main feature." This must read as a game-like world you operate, never as a dashboard.
- AAA game feel with low RAM/CPU. 2D isometric canvas, not a heavy 3D engine.
- Any scripted or pre-recorded element in the demo must be labeled as such. No simulated data presented as live.

## Premises

1. The city is the interface, not a dashboard or picture: you act on districts and agents there.
2. Meaning in plain English outranks code; code is drill-down only.
3. MVP is one repo, one live scene: the map builds, session CRUD works, an agent visibly works and reports in English, and one real drag action on the city starts real agent work. (Revised in session after the second opinion: no drag action risked "CodeCity with avatars.")
4. Lightweight beats AAA fidelity: game feel, low RAM/CPU.

## Approaches Considered

### Approach A: Graph in Costume

React Flow + ELK, illustrated district nodes, one agent CLI adapter, server-sent events. Fastest slice, free pan/zoom/drag. Rejected: judges may file it as a dashboard or graph editor in 30 seconds, which is the anti-project trap, and game feel has a hard ceiling.

### Approach B: Isometric City Engine

PixiJS 2.5D isometric city. dependency-cruiser/ts-morph extraction, directory-first districts (Louvain only as a tested candidate refinement, see Committed Contracts), Llama naming and reports, WebSocket event stream, one git worktree per session, drag-connect dispatches a real task. Costs real layout, camera, and sprite work, and a bad tileset reads as a toy. Grows into the 10x version (multi-repo city sim) without a rewrite.

### Approach C: Future Preview City

Approach B plus a plan layer: requested features appear as translucent buildings, affected districts light up, approval starts construction, verified work turns solid. Strongest 3-minute story and the natural home for Claude's collision footprints. Rejected for the submission: footprint prediction is the hardest semantic problem here, and wrong previews damage trust. It stays out of scope (see Committed Contracts).

## Recommended Approach

Approach B, because the anti-dashboard rule and the lightweight-AAA premise are both existential. C's preview idea is explicitly out of submission scope. TS/JS monorepos first. One coding-agent CLI adapter first. Llama for district naming, narration, and diff-to-English reports, which is also the Meta AI tooling surface.

Open rule check before committing the agent runtime: confirm what counts for "Use of Meta AI tooling" and whether the coding agent itself must run on a Meta model. That answer decides OpenHands/Llama versus a stronger model for edits with Llama on the city layer.

## Committed Contracts (added after spec review round 1)

### Finish flow
A session ends in one of three user decisions on its district report card: Accept, Discard, or Keep for later. Accept shows the diff summary in English, the changed buildings, and test status; the user confirms, then the session branch merges into the main checkout. A merge conflict or failing checks blocks Accept and shows the conflicting buildings with two choices: send the same agent back to fix it, or discard. Discard deletes the worktree and branch after one explicit confirmation. Keep for later leaves the worktree untouched and the district marked finished-unmerged. Nothing merges without the user's Accept.

### Drag-connect contract
Dragging a road from district A to district B means: "make B able to use A." It generates the task text "Connect B to A so B can use A's <plain-English purpose>", shown in an editable confirmation card before anything runs. The user can edit the task, change the target district, or cancel; no agent starts before confirmation. Direction matters: the road points from the used district to the using district. Same-district drags, duplicate existing connections, and drags onto a district with a running session that already touches it are rejected in the UI with a reason. Deleting a drawn road before confirmation cancels; deleting an existing road only proposes a task, it never edits code directly.

### Session lifecycle
- Create: makes a git worktree and branch, starts one agent process, state = working.
- Pause: stops the agent process; state and English history stay in SQLite. Resume restarts the CLI with its stored session id (`claude --resume <id>`; Codex equivalent verified in the day-1 spike) in the same worktree and conversation. State = paused. (Restated D10: process suspension is not the mechanism.)
- Stop: ends the agent process; work in the worktree is kept and can still be accepted or discarded. State = stopped.
- Update: renaming a session, editing its task note, or sending a follow-up instruction to a working or paused session. It never changes another session.
- Delete/Archive: archiving a working session stops its agent first (with confirmation), keeps the report and English history, and removes the worktree only if the user also chooses discard. Archive never silently deletes unmerged work; it lists what will be lost.

### Failure behavior
- Stalled: no agent event for a set interval shows the worker idle with a "no news" marker, plus Nudge (send a follow-up) and Stop.
- Crashed: the district shows a stalled-construction state, the last real event, and Restart or Discard.
- Unlocatable: events that cannot be mapped to a building keep the worker at the district gate marked "location unknown." It never invents a building.
- Failed edits or failing tests: the affected buildings show a failed state and the report says what failed in English, with Send back to fix or Discard.
- Report generation fails: the user gets the raw event list and diff stats with a "report unavailable" label and a retry. A session never shows a polished report that was not generated from its real diff.

### Districts and connections
Districts are directory-first: top-level packages/apps (workspace packages in a monorepo) are districts, because they are stable and explainable on a messy repo. Import-graph community detection (Louvain) is only a candidate refinement, tested on the friend's repo in the day-1 spike; it ships only if it produces districts a viewer can name. If clustering produces unusable districts, directory districts stand and nothing in the UI depends on Louvain.
Connections are factual import edges extracted with the Oxc parser/resolver in Rust (Node extraction tools were rejected with the Node backend, see Decision ledger): A imports B. An edge's plain-English label is generated by Llama from the actual imported symbols and file names, and is marked as an explanation, not a fact. Inferred connections (Llama suspects a relation with no import edge) are never drawn as roads; they can appear only as suggestions in a district card, labeled as guesses.

### Runtime fallback split
- If the Meta AI tooling rules require the code-editing agent to run on a Meta model: the agent runs on the required model, and the live loop, event mapping, and reports stay identical. Demo tasks are then chosen small enough for that model, rehearsed in advance.
- If the rules allow any agent model: a stronger coding model or existing coding-agent CLI edits code; Llama runs naming, narration, and reports.
- If Llama is unavailable, slow, or weak: districts fall back to deterministic names from folder/package names, and reports fall back to a template built from the real diff (files changed, tests run, results). The city and sessions keep working with no model calls.

### Safety model
Agents run only inside their session worktree. Starting a session is the approval to read and edit inside that worktree. Anything outside it (installing packages, network calls, deleting files outside the worktree, git push, changing repo config) requires a user confirmation shown in plain English before it runs. Secrets: model and agent credentials come from the user's environment or OS keychain, are never written into the repo, the session store, or reports, and are redacted from event logs. Repo content is data, not instructions: text inside the target repo cannot grant the agent new permissions.

### Scope decision on Approach C
Collision footprints, footprint prediction, and the translucent future preview are OUT of the MVP and out of the submission scope. No success criterion depends on them. Overlap detection from real events (below) is committed MVP behavior, not an Approach C promotion: it uses only files actually touched, never predicted footprints.

### Overlap without prediction
The MVP detects overlap from real events, not predictions: when two working sessions touch the same file or district, both districts show an overlap marker naming the other session. On Accept, if the two branches diverge on the same files, the finish flow's conflict path applies. There is no merge prediction in the MVP.

### Map stability
Extraction, layout, and naming are computed when a repo is opened and then frozen for the session view. New files from a working agent appear as new buildings at the edge of their district; changed buildings update state in place. Districts never move, merge, or get renamed while any session is working. A full re-layout only runs on an explicit user action when no session is working.

### Event pipeline and limits
First agent adapter: Claude Code CLI (`claude -p` with streaming JSON output) as primary, Codex CLI (`codex exec --json`) as the one fallback. The day-1 spike pass condition, verified before the live loop is built on either: the CLI emits a stable session id, per-tool file paths for edits, command and test outcomes, and a resume mechanism for a paused session. Whichever CLI passes is the demo adapter; if neither passes the file-path condition, sessions render at district level marked "location unknown" and that CLI is not used for the demo. Pause/resume, normalized events, and worker location all depend on this spike result, not on assumed CLI behavior. If the Meta AI tooling rule check requires a Meta-model agent, the runtime fallback split above governs which model drives edits; the adapter contract (events listed here) stays the same. Normalized events: session started, file touched (path), command run, test result, agent message, session finished/failed. If a CLI cannot emit file-touched events, its worker stays at district level marked "location unknown" and that CLI is not used for the demo. Supported limits for the hackathon: repos up to roughly 2,000 source files, at most 3 concurrent sessions, target 60 fps pan/zoom and under 500 MB RAM for the app itself (excluding agent processes) on the demo machine, checked at the day-3 gate.

### Ten-day capacity and cut order
Capacity assumption to confirm at kickoff: a small team (up to 4) with AI-assisted build. Order: day 1 rule check plus two spikes (repo-to-districts, agent event stream); days 2-3 live loop and kill criterion; days 4-5 session CRUD, finish flow, failure states; day 6 drag-connect; day 7 overlap marker and demo-repo rehearsal; days 8-9 visual polish after the moodboard gate; day 10 demo recording and submission. Cut order if late: (1) polish and particles, (2) pause/resume (stop only), (3) Louvain refinement, (4) overlap marker. Never cut: real event mapping, finish flow, failure states, English reports, drag-connect dispatch (D9).
